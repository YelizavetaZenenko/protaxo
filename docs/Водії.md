# Водії (Driver)

Водій, прив'язаний до [[Контрагенти|контрагента]]. Пакет `com.example.protaxo.driver` не змінився, але **окремої вкладки/сторінки в UI більше немає** — за проханням користувача керування водіями повністю перенесено на сторінку перегляду контрагента (`GET /clients/{id}`), розділ "Водії". `DriverPageController` (сторінки `/drivers`, `/drivers/new`, `/drivers/{id}/edit`) і шаблони `drivers/list.html`/`drivers/form.html` **видалені**; `DriverFormData` теж видалено як більше не використовуваний.

## Поля

- `clientId` — FK на [[Контрагенти]]
- `fullName` — обов'язкове (`@NotBlank`)
- `phone` — **обов'язкове** й валідується форматом (`@NotBlank` + `@Pattern` у `DriverRequest`, за проханням користувачки — "рівно по скрипту, якщо цифр менше — не дозволяти зберігати"). Раніше було опційне без формату. Точний формат-регулярка змінювався двічі 2026-09-07 — див. [[#Формат телефону]] нижче для повної історії й механізму. Валідація на СЕРВЕРІ (тому діє для **всіх** місць, що створюють водія — і `clients/view.html`, і `clients/form.html`, і модалка "+ Додати нового водія" на формі [[Наряд-заказ]]), і продубльована на клієнті в `clients/view.html`/`clients/form.html` (та сама регулярка через спільний `ProtaxoPhone.PATTERN`, показує помилку в модалці одразу, без звернення до сервера) — модалку на формі наряд-заказу клієнтською валідацією поки не оновлено (лише маска вводу), але серверна все одно не пропустить некоректний телефон звідти теж

## Формат телефону

**Друга ітерація формату (2026-09-07, пізніше того ж дня)** — користувачка спершу попросила формат "лише цифри, `+380XXXXXXXXX`" (без розділових знаків) для [[Контрагенти|contactPersonPhone контрагента]], а трохи згодом — **інший, з дужками й дефісами, і для всіх номерів у системі**: `+38(0XX)-XXX-XX-XX`. Це стосується `Driver.phone`, `Client.contactPersonPhone` і `Client.phone` (загальне поле) одночасно — не лише полів, показаних безпосередньо на формі водія.

**Регулярка**: `^\+38\(0\d{2}\)-\d{3}-\d{2}-\d{2}$` — буквальні дужки й дефіси в конкретних позиціях, `0` одразу після відкриваючої дужки обов'язковий (код оператора завжди починається з нуля в українській мобільній нумерації). Повний набір цифр (10: `0XX` + `XXX` + `XX` + `XX`) — той самий вміст, що раніше зберігався як `+380XXXXXXXXX` (9 цифр після `+380`), просто з доданим початковим `0` і розділовими знаками; наприклад `+380671112233` → `+38(067)-111-22-33`.

### Спільна JS-маска (`window.ProtaxoPhone`, `fragments/topbar.html`)

На відміну від решти дрібного JS на сторінках (навмисно дубльованого по кожній сторінці, за стилем проєкту), функція форматування телефону тепер **спільна й глобальна** — підключена в `fragments/topbar.html` (той самий фрагмент, що вже містить `createDraftStore`), бо задіяна одразу в шести полях у чотирьох шаблонах (`clients/form.html` — `contactPersonPhone`/`employeePhone`/`driverPhone`, `clients/view.html` — `driverPhone`, `invoices/form.html` — `newClientPhone`/`newDriverPhone`). Дублювати таку логіку шість разів визнано зайвим, той самий аргумент, що вже застосовувався для `createDraftStore`.

- `window.ProtaxoPhone.mask(input)` — вішає `input`-listener, що на кожне натискання перебудовує значення поля з нуля з "сирих" цифр: прибирає все, крім цифр; якщо рядок починається з `38` (користувач набрав повний код країни) — прибирає ці два символи; лишає перші 10 цифр; збирає `+38(XXX)-XXX-XX-XX`, дописуючи дужки/дефіси по мірі набору (закриваюча дужка з'являється після 3-ї цифри, і т.д.) — тому проміжний стан під час набору (`+38(0`) виглядає природно, не як помилка
- `window.ProtaxoPhone.PATTERN` — та сама регулярка, що на сервері, повторно використовується для клієнтської валідації там, де вона є (`clients/form.html`/`clients/view.html`, модалка водія — `phonePattern.test(phone)` перед `fetch`)
- Маска не гарантує коректність сама по собі (наприклад, не змушує починати з `0` після дужки) — фінальна перевірка завжди на сервері (`@Pattern`); маска — лише зручність під час набору

### Міграція існуючих даних — `V27__reformat_phone_numbers.sql`

Стара сесія (раніше того ж дня) вже зберегла частину телефонів у форматі `+380XXXXXXXXX` (тестові водії/контрагенти). Щоб не заблокувати редагування цих записів новою суворішою валідацією (сервер відхиляв би `PUT`/`POST` зі старим форматом, навіть якщо користувач не чіпав саме поле телефону), написана міграція даних — `UPDATE ... SET phone = regexp_replace(phone, '^\+380(\d{2})(\d{3})(\d{2})(\d{2})$', '+38(0\1)-\2-\3-\4') WHERE phone ~ '^\+380\d{9}$'` — окремо для `drivers.phone`, `clients.contact_person_phone`, `clients.phone`. Значення, що **не** відповідали навіть старому суворому формату (сміттєві тестові дані на кшталт `"123333"`) **свідомо лишені як є** — вони не проходили валідацію й раніше, виправляти їх мало сенс лише вручну при наступному редагуванні.

## Де тепер живе UI

На `clients/view.html` — таблиця водіїв контрагента (`driverService.findByClientId(id)`, рендериться сервером при першому завантаженні сторінки) + кнопка "+ Додати водія" і кнопки "Редагувати"/"Видалити" в кожному рядку. Усе подальше керування (додавання, редагування, видалення) — **суто через `fetch` до вже наявного REST API**, без жодних нових серверних сторінок:

- **Додати** — модальне вікно (ПІБ і телефон обов'язкові, телефон звіряється з `^\+380\d{9}$` на клієнті перед відправкою) → `POST /api/drivers`
- **Редагувати** — те саме модальне вікно, попередньо заповнене з `data-*` атрибутів рядка → `PUT /api/drivers/{id}`
- **Видалити** — стилізована модалка підтвердження (`#confirmModalOverlay`, спільна функція `showConfirm(message, onConfirm)`) замість браузерного `confirm()` — за проханням користувачки ("підказка... повинна гарно виглядати, а не як зараз у вигляді вспливаючого вікна"); підтвердивши, викликає `DELETE /api/drivers/{id}` (ADMIN-only на рівні `SecurityConfig`, кнопка також схована через `sec:authorize` для не-ADMIN). `showConfirm` — невеликий переніспользуваний хелпер, продубльований в обох шаблонах (`clients/view.html`, `clients/form.html`), а не винесений у спільний файл — узгоджено зі стилем проєкту (кожна сторінка має власний inline `<script>`)

Жодних нових Java-контролерів для цього не знадобилось — `DriverController` (REST, `/api/drivers`) уже мав повний CRUD (`GET`/`POST`/`PUT`/`DELETE`) ще з часу, коли існувала стара сторінка `/drivers`; тепер той самий контролер обслуговує UI напряму з клієнтського JS.

## Використовується в

- `GET /api/clients/{clientId}/drivers` (`client.web.ClientLookupController`, метод `DriverService.findByClientId`) — підтягує водіїв обраного контрагента для випадаючого списку в полі "Водій" на вкладці "Наряд" у [[Наряд-заказ|Наряд-заказі]]. Це **не FK-зв'язок**: поле в Invoice лишається вільним текстом, лише джерело варіантів тепер звужене до реальних водіїв контрагента — див. [[Наряд-заказ]]
- `POST`/`PUT`/`DELETE /api/drivers` — тепер використовується і модальним вікном на сторінці [[Контрагенти|Контрагента]] (основний спосіб керування), і модальним вікном "+ Додати нового водія" прямо з форми наряд-заказу

Раніше також використовувався модулем "Наряди" (Order) — той модуль **повністю видалений**, див. [[Рішення і відхилення]].
