# Рішення і відхилення від оригінальної специфікації

`ARCHITECTURE.md` (корінь репозиторію) — початковий бриф. Фактична система відрізняється в кількох свідомих місцях.

## Sesійна автентифікація замість JWT

Специфікація каже "Spring Security + JWT". Побудовано сесійну автентифікацію (форма логіну) + HTTP Basic для API.

**Чому**: JWT має сенс для окремого SPA/мобільного клієнта. Обрали Thymeleaf (серверний рендеринг) — для нього ідіоматичний підхід саме сесія+cookie, а не токен. Basic Auth додано паралельно, щоб API й далі можна було тестувати з Postman/curl без танців з токенами.

**Коли переглянути**: якщо колись з'явиться окремий React/мобільний фронтенд — тоді JWT стане доречним.

## Thymeleaf замість React

Специфікація сама зазначає React як "на майбутнє". Обрали Thymeleaf для швидкого старту мінімального UI без окремого фронтенд-білда.

## Spring Boot 4.1.0 замість 3.x

Проєкт стартував уже на новішій версії. Наслідок: autoconfigure розбитий на дрібні модулі — знадобилась додаткова залежність `spring-boot-flyway`, якої не було потрібно в Boot 3.x. Див. [[Технологічний стек]].

## Контрагент замість Клієнта

Специфікація: `Client { id, name, edrpou, contacts, defaultPaymentType }`.
Фактично: прибрано `contacts` і `defaultPaymentType`, додано `fullName` (повна юридична назва) і `contactPersonName` (ім'я контактної особи). UI перейменовано "Клієнти" → "Контрагенти" по всій системі.

**Чому**: пряма вимога користувача — потрібна була саме така структура даних для контрагента, поля контактів/оплати виявились незатребуваними.

## Наряд-заказ (Invoice) — модуль поза специфікацією

Специфікації немає взагалі. Це окремий документ продажу (на кшталт видаткової накладної): номер, дата/час (авто), організація, контрагент, вкладка "Наряд" (авто/водій/відповідальні — вільний текст із автопідказками, що запам'ятовуються), вкладка "Товари" (позиції з [[Каталог|каталогу]], автопідрахунок).

**Чому**: пряма вимога користувача, окремо від наявного на той момент модуля "Наряди" (Order).

**Важливо**: `Наряд-заказ` і колишні "Наряди" були **двома незалежними, не пов'язаними між собою** модулями. `Наряд-заказ` частково перекривав ідею `OrderItem` зі специфікації, але не був прив'язаний до `Order`. За явним рішенням користувача каталог був підключений **лише** до `Наряд-заказу`, не до `Наряд`.

## "Відповідальний за транспорт" → "Відповідальний за ремонт"

Поле на вкладці "Наряд" [[Наряд-заказ|Наряд-заказу]] перейменоване за прямим проханням користувача — і в UI-підписі, і на рівні коду (`Invoice.transportResponsibleName` → `repairResponsibleName`, колонка БД, `FieldSuggestionCategory.TRANSPORT_RESPONSIBLE` → `REPAIR_RESPONSIBLE`, з міграцією даних наявних підказок). Зроблено повне перейменування, а не косметичну зміну лише підпису — узгоджено зі стилем проєкту (немає "мертвих" старих назв полів у коді, як і при перейменуванні "Клієнти" → "Контрагенти").

## Модуль "Наряди" (Order) — повністю видалений

Пізніше користувач прямо попросив **повністю видалити вкладку "Наряди"**. Видалено весь пакет `com.example.protaxo.order` (entity/dto/mapper/repository/service/controller/web), шаблони `templates/orders/`, посилання в навігації, і сама таблиця `orders` у БД (`V20__drop_orders.sql`, `DROP TABLE`). Разом з модулем прибрано й `client.entity.PaymentType` (enum `CASH/CARD/INVOICE`) — він використовувався лише в `Order.paymentType` і після видалення модуля лишився мертвим кодом без жодних посилань.

**Чому**: пряма вимога користувача — модуль не використовувався і лише захаращував навігацію та довідку.

**Наслідки для решти системи**: [[Договори]], [[Водії]], [[Автомобілі]] втратили свій єдиний "споживач" FK (`contractId`/`driverId`/`vehicleId` в Order) і зараз існують як самостійні довідники без інших модулів, що на них посилаються напряму через FK — крім нового непрямого використання Водіїв/Автомобілів через `ClientLookupController` (звуження автопідказок [[Наряд-заказ|Наряд-заказу]] за контрагентом, без FK). "Акт виконаних робіт" (відкладена ідея з [[Що ще зробити]]) тепер однозначно генерується лише на основі [[Наряд-заказ|Наряд-заказу]] — альтернативи "Наряд без цін" більше не існує.

## Order.orderNumber — спрощення

Специфікація: номер присвоюється лише при переході статусу Draft → In Progress ("присвоюється постійний номер").
Фактично: номер обчислюється на льоту з `id` (`№%06d`) одразу, для будь-якого статусу. Повний життєвий цикл статусів (блокування полів, заборона видалення "в роботі" тощо) **не реалізований** — `OrderStatus` це просто enum без guard-логіки.

## openhtmltopdf замість Flying Saucer

Специфікація: "Thymeleaf + Flying Saucer / OpenPDF". Використано **openhtmltopdf** — активно підтримуваний форк саме Flying Saucer (той самий підхід: XHTML+CSS напряму в PDF), а не оригінальну бібліотеку, яка практично не розвивається роками. Деталі — [[PDF-генерація]].

Повний перелік того, що ще не зроблено взагалі — [[Що ще зробити]].
