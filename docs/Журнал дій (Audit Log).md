# Журнал дій (Audit Log)

Логування всіх CRUD-дій (створення/редагування/видалення) в усіх бізнес-модулях. Пакет `com.example.protaxo.audit`.

## Рівень деталізації

**По-польові діфи тепер усюди (2026-09-14)** — раніше повний діф (старе значення → нове) писався **точково** лише для [[Автомобілі|Vehicle]] і [[Тахографи|Tachograph]] (щоб показати позначку "змінено" в їхніх таблицях), решта модулів логувала тільки подію ("хто/що/коли", без деталей). За проханням користувача той самий механізм (`FieldDiff` + перевантаження `AuditLogService.record(..., changes)`) тепер підключено **в кожному** сервісі, що пише в журнал: [[Контрагенти|Client]], [[Автомобілі|Vehicle]], [[Договори|Contract]], [[Водії|Driver]], [[Тахографи|Tachograph]], [[Наряд-заказ|Invoice]], [[Каталог|CatalogItem]], `CalibrationProtocol`, `ProfileService` (власний профіль користувача). Через це відповідний пункт у [[Що ще зробити]] ("Hibernate Envers / по-польові діфи") тепер закритий — без Envers, ручним `FieldDiff` у кожному сервісі, узгоджено зі стилем проєкту (явний код, не фреймворкова магія).

Виняток — **пароль** (`ProfileService.updateProfile`): значення в діф **не потрапляють** ніколи, лише синтетичний запис `"Пароль": ["***", "***"]`, якщо пароль дійсно змінювався — щоб сам факт зміни був видний у журналі, але ніде не зберігався жоден натяк на сам пароль (ні старий, ні новий, навіть хеш).

`Contract` — виняток іншого роду: єдине "своє" поле, яке можна редагувати — це, по суті, FK на контрагента (`clientId`), тому діф показує саме **назву контрагента** ("було"/"стало"), а не сирий id.

**Було спочатку (2026-09-09)** — додано **точково** для [[Автомобілі|Vehicle]] і [[Тахографи|Tachograph]], за проханням користувача показати позначку "змінено" прямо в таблицях цих двох розділів:

- `AuditLog` отримала нову nullable-колонку `changes` (`TEXT`, міграція `V34__add_audit_log_changes.sql`) — JSON-рядок формату `{"Лейбл поля": ["старе значення", "нове значення"]}`, серіалізується/десеріалізується через Jackson (`tools.jackson.databind.ObjectMapper` — **Jackson 3.x у цьому проєкті, не 2.x**: пакети `tools.jackson.*`, не `com.fasterxml.jackson.databind.*`/`.core.type.*`; лише `jackson-annotations` лишився під старим `com.fasterxml.jackson.core`. Прийшло транзитивно через `spring-boot-starter-jackson`, окрему залежність у `pom.xml` додавати не довелось)
- Новий спільний хелпер `common.util.FieldDiff` (білдер `.add(лейбл, старе, нове).add(...)....build()`) — порівнює через `Objects.equals(toString())`, кладе в мапу **лише** поля, що реально відрізняються. Викликається в `VehicleService.update()`/`TachographService.update()` **до** `mapper.updateEntity(...)` (поки в сутності ще старі значення), результат передається новим перевантаженням `AuditLogService.record(action, entityType, entityId, Map<String,String[]> changes)`
- `AuditLogService.findLatestChanges(entityType, entityId)` — дістає діф з **останнього** запису з непорожнім `changes` для цієї сутності (новий похідний метод репозиторію `findFirstByEntityTypeAndEntityIdAndChangesIsNotNullOrderByOccurredAtDesc`); повертає порожню мапу, якщо сутність ніколи не редагувалась або останні правки нічого фактично не міняли
- `VehiclePageController.list()` наперед будує `vehicleChanges`/`tachographChanges` (`Map<Long, Map<String,String[]>>`, по одному запиту `findLatestChanges` на рядок — прийнятно для очікуваних обсягів цих двох таблиць, без спеціальної батч-оптимізації) — обидві мапи, разом з рештою даних для `/vehicles`, використовуються в `vehicles/list.html`
- У шаблоні — маленька кругла позначка `.change-badge` (CSS, помаранчева крапка) поруч зі значенням **кожного** поля, яке фігурує в мапі змін для цього рядка; `title`-атрибут (нативний тултип браузера, без JS) показує "Було: X → Стало: Y". Перевірено на VIN, Номер кузова, Держномер, Марка, Модель, Рік випуску (Vehicle) і Виробник, Модель, Заводський номер, Дата випуску (Tachograph) — Контрагент/Автомобіль (зв'язки, не власні поля) цим механізмом не покриті

## Сторінка `/audit-log`: українські підписи, "Елемент" замість голого ID (2026-09-14)

За проханням користувача, якому не була зрозуміла суть колонки "ID" (просто число сутності — незрозуміло, який саме автомобіль/контрагент/наряд це насправді):

- **Дія й Сутність — українською**: `AuditLogService.translateAction(AuditAction)` (`CREATE`→"Створено", `UPDATE`→"Оновлено", `DELETE`→"Видалено") і `translateEntityType(String)` (мапа `ENTITY_TYPE_LABELS` — сирі назви Java-класів на кшталт `"CatalogItem"` → "Позиція каталогу" і т.д. для всіх 9 типів сутностей). Обидва методи публічні саме для виклику з Thymeleaf через `@auditLogService.translateAction(...)`/`.translateEntityType(...)` — той самий підхід, що вже був у `parseChanges` для відображення діфу.
- **Колонка "ID" → "Елемент"** — новий компонент `audit.service.AuditEntityLabelResolver` (окремий клас, не в `AuditLogService`, щоб не роздувати його інжектами) підтягує людський лейбл замість сирого id: держномер для Vehicle, заводський номер для Tachograph, назва для Client/CatalogItem, номер договору/наряду для Contract/Invoice, внутрішній номер для CalibrationProtocol, ПІБ для Driver/User. Якщо елемент **ще існує** (`repository.existsById`) — лейбл клікабельний, веде на його сторінку перегляду (`/vehicles/{id}`, `/clients/{id}` тощо); Driver і User посилання не отримують — у них немає окремої сторінки перегляду (Driver керується вкладено на сторінці контрагента, User — лише список + запрошення/видалення, без власного `GET /users/{id}`).
- **"Видалено" вже не показує голий `#id`** — м'яке видалення (`@SQLRestriction("deleted_at IS NULL")`) ховає запис від звичайного `findById`, тому для DELETE-записів (і будь-чого, що зачіпає вже видалений елемент) лейбл раніше не резолвився. Кожен репозиторій отримав одну додаткову нативну SQL-вибірку в обхід цього фільтра — просте читання одного стовпця (`SELECT registration_number FROM vehicles WHERE id = :id`, не завантаження сутності через Hibernate, тому `@SQLRestriction` на неї не діє), напр. `VehicleRepository.findRegistrationNumberByIdIncludingDeleted`. Посилання на перегляд для такого елемента все одно не дається (сторінка все одно поверне 404) — лейбл показується як звичайний текст, без `<a>`.
- Голий `"#id"` лишається лише справжнім крайнім випадком — якщо навіть ця нативна вибірка нічого не знайшла (рядок фізично видалили з БД, не через застосунок).

## Прибирання "хвилястих" меж таблиці (2026-09-14)

Не специфічно для журналу, але виявлено й виправлено саме тут (таблиця з найбільшою кількістю колонок): межі рядків у **всіх** таблицях (`th, td` у `style.css`) тепер малюються через `box-shadow: inset 0 -1px 0 var(--border)`, а не `border-bottom`. При дробових коефіцієнтах масштабування екрана (девайси зі 125%/137.5% тощо) Chrome округлює `border` кожної клітинки окремо до фізичного пікселя — у таблиці з `border-collapse: collapse` це давало межу, що "зникала" в різних колонках по-різному; `box-shadow` в цей механізм не втручається. Окремо виявлено (і виправлено разом із цим): `display: flex` **прямо на `<td>`** (клас `.actions-cell`, кнопки "Редагувати"/"Видалити") зламаний за задумом — змінює тип боксу клітинки, вона перестає розтягуватись на висоту рядка. `td.actions-cell` тепер лишається справжньою `table-cell` (`display: table-cell`, відступ між кнопками через `> * + * { margin-left }`); `div.actions-cell` (тулбари сторінок перегляду поза таблицями) і далі `flex` — там це коректно.

## Подвійне зберігання

1. **Таблиця `audit_log` у БД** — джерело правди для UI-сторінки адміна (`/audit-log`, пагінація по 50 записів, найновіші зверху). Ніколи не редагується й не видаляється — `AuditLog` не має soft delete, це строго append-only.
2. **Окремий файл** `logs/audit.log` (з ротацією по днях, зберігання 90 днів) — незалежна копія на диску через окремий Logback-логер `"AUDIT"` (`logback-spring.xml`, `additivity="false"`, щоб не змішувався зі звичайними логами застосунку). `logs/` в `.gitignore`.

## Як підключено

`AuditLogService.record(action, entityType, entityId, [changes])` викликається **явно** в кінці кожного `create()`/`update()`/`softDelete()` у сервісах ([[Контрагенти|Client]], [[Автомобілі|Vehicle]], [[Договори|Contract]], [[Водії|Driver]], [[Тахографи|Tachograph]], [[Наряд-заказ|Invoice]], [[Каталог|CatalogItem]], `CalibrationProtocol`, `User`) — без AOP/анотацій-магії, узгоджено зі стилем решти проєкту (явний код замість фреймворкових трюків). Користувач береться з `SecurityContextHolder` (email залогіненого). Модуль "Наряди" (Order) теж мав такий виклик, але повністю видалений разом із рештою модуля — див. [[Рішення і відхилення]].

## Доступ

`/audit-log` — **лише ADMIN** (і в `SecurityConfig`, і посилання в навігації сховане через `sec:authorize`). MASTER не бачить журнал, але **його власні дії туди все одно потрапляють** — обмежений лише перегляд, не сам факт логування.

## Не логується (поки)

- Вхід/вихід із системи (login/logout) — свідомо не включено в цей етап, лише CRUD. Якщо знадобиться — окремий хук на Spring Security authentication events.

Дії над `User` (запрошення, видалення, самостійна зміна профілю) вже логуються — див. [[Реєстрація акаунтів (запрошення)]].
