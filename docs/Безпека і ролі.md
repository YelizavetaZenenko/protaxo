# Безпека і ролі

## Автентифікація

Сесійна (форма логіну `/login`) для сайту + **HTTP Basic** одночасно для API/Postman-тестування (`SecurityConfig`). Це свідоме відхилення від JWT, зазначеного в оригінальній специфікації — див. [[Рішення і відхилення]].

- CSRF **увімкнено** для всіх сторінок сайту (Thymeleaf автоматично вставляє прихований `_csrf` в кожну `<form th:action="...">`)
- CSRF **вимкнено** для `/api/**` (щоб Postman/curl з Basic Auth могли робити POST/PUT/DELETE без токена)

## Ролі

Enum `Role { ADMIN, MASTER }` на сутності `User` (`security` модуль). **З 2026-09-21 enum має поле `label`** ("Адміністратор"/"Майстер") — на формі запрошення/редагування користувача (`users/form.html`) і в списку (`users/list.html`) UI показує `r.label`, а не сирий `name()` англійською; сама роль у БД/бекенді й далі зберігається як `ADMIN`/`MASTER` (`Enumerated(EnumType.STRING)`), українська — тільки шар відображення.

Більшість правил і досі захардкоджені в `SecurityConfig`, але **два з них (журнал дій, керування користувачами) тепер гнучкі через `Role_Permissions`** (JSON, 2026-09-20) — див. розділ нижче:

```java
.requestMatchers("/css/**", "/images/**", "/login", "/accept-invite").permitAll()
.requestMatchers("/audit-log/**").access(requiresPermission(PermissionKey.CAN_VIEW_AUDIT_LOG))
.requestMatchers("/users/**").access(requiresPermission(PermissionKey.CAN_MANAGE_USERS))
.requestMatchers(HttpMethod.DELETE, "/api/**").hasRole("ADMIN")
.requestMatchers(HttpMethod.POST, "/api/repair-workers").hasRole("ADMIN")
.requestMatchers(HttpMethod.POST, "/api/master-cards").hasRole("ADMIN")
.requestMatchers(HttpMethod.POST, "/*/*/delete").hasRole("ADMIN")
```

Тобто: **видалення** (REST DELETE і веб-форми `/{модуль}/{id}/delete`), **додавання нового робітника** (`POST /api/repair-workers`, довідник для полів "Відповідальний за ремонт"/"Керівник ремонту" в [[Наряд-заказ]]) і **додавання нової майстер-картки** (`POST /api/master-cards`, довідник "Номер картки"/ПІБ власника для [[Протокол калібрування (CalibrationProtocol)]], той самий "add-to-dictionary" патерн, що й repair-workers) — і досі жорстко тільки ADMIN, без винятків. **[[Журнал дій (Audit Log)|журнал дій]]** і **керування користувачами** (`/users`) — за замовчуванням теж тільки ADMIN, але тепер можна відкрити й для MASTER через UI, без деплою нового коду. `/css`, `/images`, `/login`, `/accept-invite` — публічні (людина ще не залогінена), `/accept-invite` — див. [[Реєстрація акаунтів (запрошення)]]. Все інше (перегляд/створення/редагування) — будь-який автентифікований користувач.

**Приклад окремого, не-CRUD правила** (`POST /api/repair-workers`/`POST /api/master-cards` — це не видалення й не звичайний `/{id}/delete`, тому потребують власного окремого рядка в `SecurityConfig`, на відміну від видалень, які покриваються загальним патерном): якщо в майбутньому з'являться інші подібні "точкові" ADMIN-обмеження (не CRUD-delete), додавати такими ж окремими `requestMatchers`, а не намагатися підлаштувати загальні патерни.

У Thymeleaf кнопки видалення (і решта захардкоджених ADMIN-only елементів — довідники робітників/майстер-карток) додатково ховаються для не-ADMIN через `sec:authorize="hasRole('ADMIN')"` — але це лише UX, реальний захист на сервері.

## Role_Permissions — гнучкі права (2026-09-20)

Реалізовано мінімальний зріз оригінальної ідеї зі специфікації (`ARCHITECTURE.md`: "roleName, permissions (JSON з детальними правами)"), обмежений двома реальними потребами (не спекулятивний повний набір "can_create_order" тощо — тих полів ніхто не просив і вони не відповідають поточному функціоналу):

- **На рівні ролі, не індивідуально** — усі MASTER мають однаковий набір прав, вирішено користувачкою явно.
- **ADMIN завжди має повний доступ** — хардкод у `PermissionService.roleHasPermission()`, не читається з таблиці. Це навмисно: інакше адмін міг би сам собі випадково заблокувати керування системою через той-таки екран /users.
- **Два перемикачі для MASTER**: `canViewAuditLog`, `canManageUsers` — за замовчуванням `false` (той самий стан, що й до цієї фічі).

**Схема** (`RolePermissions extends BaseEntity`, `V37__init_role_permissions.sql`):
```sql
CREATE TABLE role_permissions (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    role VARCHAR(20) NOT NULL UNIQUE,
    permissions TEXT NOT NULL,   -- JSON-рядок, не jsonb-колонка
    ...
);
```
`permissions` — **`TEXT`, не Postgres `jsonb`**, з `AttributeConverter<Map<String,Boolean>,String>` (`PermissionsJsonConverter`) поверх Jackson `ObjectMapper`. Свідомий вибір простоти: `ddl-auto=validate` вимагає, щоб Hibernate-мапінг типу точно збігався з типом колонки в міграції — нативний `@JdbcTypeCode(SqlTypes.JSON)` на Hibernate 7 для цього проєкту не перевірявся, а `TEXT` + ручний converter гарантовано валідний і однаково розв'язує головну задачу ("новий permission — новий ключ у JSON, без нової міграції").

**Spring Boot 4 / Jackson 3 пастка**: пакет тепер `tools.jackson.databind.*`, не `com.fasterxml.jackson.databind.*` (лишився на старому груп-ID тільки `jackson-annotations`). Виявлено якраз на цій фічі — перша реальна серіалізація JSON у проєкті, `spring-boot-starter-webmvc` тягне `tools.jackson.core:jackson-databind:3.x` транзитивно.

**Перевірка авторизації** — `SecurityFilterChain` не підтримує динамічні (з БД) перевірки через звичайний `hasRole(...)`, тому для `/audit-log/**` і `/users/**` замінено на `.access(AuthorizationManager<RequestAuthorizationContext>)` — лямбда, що звертається до `PermissionService.hasPermission(authentication, key)`. Видимість пунктів меню (`topbar.html`) — через два нових глобальних `@ModelAttribute` в `CurrentUserModelAdvice` (`canViewAuditLog`, `canManageUsers`), той самий патерн, що вже був для `currentUser`.

**UI для адміна** — секція "Права ролі MASTER" прямо на `/users` (нова картка між таблицею користувачів і довідником робітників), `POST /users/permissions`. Свідомо без окремого дозволу на "хто може міняти ці permissions" — той самий `canManageUsers`, що відкриває сторінку, дозволяє й редагувати перемикачі; для масштабу двох ролей і одного власника системи це прийнятно, не окрема проблема, яку варто розв'язувати завчасно.

**UI сховано (2026-09-20)** — користувачка попросила прибрати секцію "Права ролі MASTER" з `/users`, щоб не було видно. Прибрано лише розмітку картки з `users/list.html`; бекенд (`PermissionService`, `POST /users/permissions`, таблиця `role_permissions`) лишився без змін і повністю робочий — просто немає візуального входу для перемикання через UI. Якщо колись знадобиться повернути — форма й контролер уже готові, досить повернути картку в шаблон.

**Що НЕ зроблено**: інші жорсткі ADMIN-only правила (видалення, робітники, майстер-картки) залишені як є — користувачка explicit підтвердила, що поки міняти лише журнал дій і керування користувачами.

### Баг: MASTER з `canManageUsers` міг підвищити собі роль до ADMIN (знайдено й виправлено 2026-09-21)

Знайдено під час навмисного аудиту коду на баги. `/users/**` захищений лише правом `CAN_MANAGE_USERS` — а `UserManagementService.invite()`/`update()` ніяк не обмежували, яку саме `role` не-ADMIN викликач може призначити. Якщо ADMIN колись вмикав перемикач "керування користувачами" для MASTER (задуманий лише для списку користувачів/журналу дій, **не** для видачі прав адміністратора), той MASTER міг одним `POST /users/{ownId}/edit` виставити собі `role=ADMIN` — повне підвищення привілеїв, без жодної додаткової перевірки.

**Виправлено**: новий приватний метод `UserManagementService.requireAdminToAssign(Role)`, викликається на початку і `invite()`, і `update()` — якщо форма просить роль `ADMIN`, а поточний автентифікований користувач не має `ROLE_ADMIN` серед `Authentication.getAuthorities()`, кидається `BusinessRuleException("Лише адміністратор може призначити роль адміністратора")`. Перевірка за реальною роллю виклику (authorities), а не за дозволами з `RolePermissions` — саме тому, що дозвіл "керувати користувачами" й право "видавати роль адміністратора" — це різні речі, які помилково злилися в одну перевірку доступу до `/users/**`.

## Останній вхід (2026-09-21)

`User.lastLoginAt` (`Instant`, nullable, `TIMESTAMPTZ` — `V40__add_user_last_login_at.sql`) — показується новою колонкою "Останній вхід" у `/users` (`dd.MM.yyyy HH:mm`, чи "Ще не входив(ла)", якщо `null` — акаунт запрошений, але жодного разу не заходив).

**Оновлюється через `LoginTrackingListener`** (`@EventListener` на `AuthenticationSuccessEvent`), а не кастомним `AuthenticationSuccessHandler` у `SecurityConfig` — Spring Security публікує цю подію для **будь-якої** успішної автентифікації (форма логіну й HTTP Basic однаково), тому один слухач покриває обидва механізми без зміни `filterChain`.

**Bulk-update (`UserRepository.updateLastLoginAt`, JPQL `UPDATE`), а не `load → setLastLoginAt → save`** — навмисно, щоб вхід у систему не зачіпав `@Version`/`updatedAt` користувача через `AuditingEntityListener` (інакше кожен логін виглядав би в даних як "редагування" запису користувача, хоча ніхто нічого не міняв).

## Баг: гонка станів у перевірці "не можна прибрати останнього адміністратора" (знайдено й виправлено 2026-09-21)

`update()`/`delete()` перевіряли `userRepository.findByRoleAndActiveTrue(Role.ADMIN).size() <= 1` без жодного блокування рядків. За точного збігу часу два одночасні запити, що знімають роль/видаляють **різних** з двох існуючих ADMIN, могли обидва прочитати count=2 (пройти перевірку) до того, як хоч один із них закомітився — результат: жодного ADMIN у системі.

**Виправлено**: новий `UserRepository.findByRoleAndActiveTrueForUpdate(Role)` з `@Lock(LockModeType.PESSIMISTIC_WRITE)` (`SELECT ... FOR UPDATE`) — блокує рядки ADMIN на час транзакції, тому другий одночасний запит чекає коміту першого і вже тоді перечитує актуальний (зменшений) count. Використовується в обох перевірках (`update`, `delete`) замість незаблокованого `findByRoleAndActiveTrue`.

## Пастка при тестуванні через curl

Без заголовка `Accept: text/html` (curl за замовчуванням його не шле) Spring Security сприймає запит як "API-клієнт" і на неавторизований доступ віддає `401` (Basic-виклик) замість `302`-редіректу на `/login`. Справжній браузер завжди шле цей заголовок, тому в реальному використанні поведінка коректна. Деталі — [[Тестування]].
