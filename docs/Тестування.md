## ⚠️ Кирилиця через curl у Git Bash на Windows

`curl -d 'текст кирилицею'` (та `--data-urlencode "поле=кирилиця"` з текстом прямо в команді) **ламає кодування** — Git Bash передає байти неправильно, і сервер або отримує "кракозябри", або (для `application/x-www-form-urlencoded`) взагалі відповідає `400 Bad Request` без пояснення, бо Tomcat суворо валідує UTF-8 при розборі параметрів форми.

**Це не баг застосунку.** Правильні способи тестувати кирилицю:

1. **Postman** — просто працює, нічого налаштовувати не треба.
2. **curl + файл** — записати значення в `.txt`-файл (UTF-8) і використати:
   ```
   curl --data-urlencode "name@шлях/до/файлу.txt" ...
   ```
   Для JSON-тіла: зберегти весь JSON у файл і `curl --data-binary "@файл.json" -H "Content-Type: application/json; charset=UTF-8"`.

Ніколи не вписувати кирилицю прямо в аргумент bash-команди — перевірено багато разів, це стабільно ламається.

**Суміжна пастка**: `cat > файл.txt <<'EOF' ... EOF` (heredoc) дописує **зайвий символ переносу рядка** в кінець файлу — `--data-urlencode "поле@файл.txt"` відправить значення разом із цим `\n`. Для короткого однорядкового значення, яке має **збігатися рівно** з чимось на бекенді (наприклад, мітка автомобіля для зіставлення "дата останнього візиту" в [[Наряд-заказ]]), зайвий `\n` ламає порівняння без жодної помилки — просто мовчки не спрацьовує збіг. Використовувати інструмент Write для такого значення (не дописує зайвих символів) замість `cat <<EOF`, коли контент піде в `--data-urlencode "поле@файл"` для порівняння "точь-в-точь".

## Пастка з `Accept: text/html`

Дет.: [[Безпека і ролі]]. Для емуляції браузера в curl:
```
curl -H "Accept: text/html" ...
```
інакше неавторизовані запити дадуть `401` замість очікуваного `302`-редіректу на логін.

## CSRF-токен для POST-форм через curl

1. GET-запит на сторінку форми з тим самим cookie-jar
2. Витягти `_csrf` зі схованого інпуту:
   ```
   grep -o 'name="_csrf" value="[^"]*"' | sed 's/.*value="//;s/"//'
   ```
3. Додати `--data-urlencode "_csrf=$CSRF"` до POST-запиту з тим самим cookie-jar

## Типова помилка при діагностиці "чому 400/500 без пояснення"

Якщо застосунок повертає `400`/`500` без стек-трейсу в консолі — це часто означає, що запит **не дійшов до Spring MVC** (падає на рівні контейнера/фільтра, наприклад через невалідний UTF-8). Щоб побачити реальну причину, перезапустити з докладним логуванням у файл:
```
.\mvnw.cmd spring-boot:run -Dspring-boot.run.arguments="--logging.file.name=D:/protaxo/app-debug.log --logging.level.org.springframework.web=DEBUG"
```
і шукати рядок `DispatcherServlet : POST "/шлях", parameters=...` — якщо його немає в логу, запит не дійшов до контролера.

## ⚠️ `<input type="date">` мовчки губить збережену дату

Поле `LocalDate` у `*FormData` **обов'язково** треба позначати:
```java
@DateTimeFormat(iso = DateTimeFormat.ISO.DATE)
private LocalDate birthDate;
```
Без цього Spring рендерить значення у форматі локалі (`3/9/85`), а `<input type="date">` приймає **лише** ISO `yyyy-MM-dd` — браузер таке значення просто відкидає й показує порожнє поле. Дата в БД при цьому збережена коректно, тому баг непомітний доти, доки хтось не відкриє форму редагування й не збереже її повторно — тоді дата затирається на порожню.

Ловиться це через curl так (перевіряти саме `value=` в HTML, а не вміст БД):
```
curl -s -b cookies http://localhost:8080/clients/6/edit | grep -o 'id="birthDate"[^>]*value="[^"]*"'
```
Знайдено при додаванні дати народження в [[Контрагенти]]; той самий баг був і в [[Протокол калібрування (CalibrationProtocol)]] (`previousInspectionDate`) — виправлено в обох.

## ⚠️ Тернарний вираз у `th:text` мусить бути ЦІЛКОМ усередині одного `${...}`

```html
<!-- НЕ ТАК — TemplateProcessingException: "Could not parse as expression" -->
<td th:text="${item.catalogItemType} == T(com.example...CatalogItemType).SERVICE ? 'Послуга' : 'Товар'"></td>

<!-- ТАК -->
<td th:text="${item.catalogItemType == T(com.example...CatalogItemType).SERVICE ? 'Послуга' : 'Товар'}"></td>
```
Все, що не всередині `${}`/`*{}`, Thymeleaf трактує як buffer-текст, а не SpEL — тернарник і виклик `T(...)` мають лишатись частиною однієї expression-обгортки. Той самий клас проблем, що вже описаний у [[Рішення і відхилення]] для конкатенації з тернарником.

Суміжна пастка на тому ж рядку: порівняння `.name() == 'SERVICE'` падає з `EL1011E: Attempted to call method name() on null context object`, якщо об'єкт може бути `null` (старі `InvoiceItem` без `catalogItem`, збережені до міграції V13). Порівнювати сам enum-об'єкт (`item.catalogItemType == T(...).SERVICE`) безпечно — оператор `==`/`equals` у SpEL коректно обробляє `null` зліва, а виклик методу на `null` — ні. Знайдено при додаванні сторінки перегляду в [[Наряд-заказ]].

## Стале зависання старого процесу

`spring-boot:run` не перекомпільовує й не вбиває попередній інстанс сам. Перед кожним перезапуском треба зупинити старий процес (`taskkill //F //IM java.exe`, або точковіше — знайти конкретний PID через `tasklist` і вбити лише його, якщо на машині є й інші, не пов'язані з проєктом, `java.exe`-процеси). Інакше новий білд може не стартувати (порт зайнятий) і curl буде бити по застарілому інстансу — виглядатиме, ніби зміни коду не подіяли.

**З 2026-09 є безпечніший спосіб запуску** — `.\scripts\run-app.ps1` (див. [[Запуск проєкту]]) сам перевіряє, що саме Docker-контейнер БД відповідає на порту, робить бекап перед стартом і лише тоді піднімає застосунок; ручний `taskkill`/`mvnw` і далі працюють для швидких ітерацій під час розробки, просто без цих перевірок.
