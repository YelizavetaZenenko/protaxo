# Запуск проєкту

## Кроки

1. Підняти базу даних і MailHog (для листів-запрошень):
   ```
   docker compose up -d
   ```
   Це піднімає контейнер `protaxo_postgres` (Postgres 16, база `protaxo`, user `postgres`, пароль `lizaliza123`, порт `5432`) і `protaxo_mailhog` (перехоплює всі листи локально, переглянути на `http://localhost:8025` — див. [[Реєстрація акаунтів (запрошення)]]).

2. Запустити застосунок **через безпечну обгортку**, а не напряму:
   ```
   .\scripts\run-app.ps1
   ```
   Вона сама: (а) блокує запуск, якщо нативний сервіс `postgresql-x64-17` активний (конфлікт портів — див. інцидент нижче), (б) піднімає Docker-контейнер, якщо він не запущений, (в) перевіряє, що в БД реально є дані (не порожня/не та копія), (г) робить свіжий бекап (`scripts\backup-db.ps1`) і лише тоді запускає `.\mvnw.cmd spring-boot:run`. Flyway автоматично накотить усі міграції з `db/migration` при старті.

   Прямий запуск `.\mvnw.cmd spring-boot:run` без обгортки й досі працює, але без жодних із цих перевірок.

3. Відкрити `http://localhost:8080` — редірект на `/login`.

## ⚠️ Важливо: конфлікт портів Postgres

На цій машині раніше стояв **нативний Windows-сервіс** `postgresql-x64-17`, який теж слухав порт 5432 і "перехоплював" з'єднання застосунку замість Docker-контейнера (обидва можуть одночасно слухати `0.0.0.0:5432` на Windows). Це призводило до того, що всі дані виглядали збереженими, але насправді жили не в тому Postgres.

**Вирішено**: нативний сервіс зупинено і переведено на ручний запуск (`Manual` startup type), щоб не піднімався сам після перезавантаження Windows. Якщо після якогось оновлення Windows/перевстановлення PostgreSQL цей сервіс з'явиться знову — перевірити:
```powershell
Get-NetTCPConnection -LocalPort 5432 -State Listen
Get-Process -Id <PID>
```
Якщо там знову `postgres.exe` (не `com.docker.backend.exe`) — зупинити службу від імені адміністратора:
```powershell
Stop-Service -Name "postgresql-x64-17" -Force
Set-Service -Name "postgresql-x64-17" -StartupType Manual
```

**Повторилось 2026-09-10**: `StartType` служби вже стояв `Manual`, але сама служба була `Running` (Manual лише вимикає автозапуск при завантаженні Windows, не гарантує, що службу хтось не запустив вручну/інсталятор PostgreSQL не запустив її після оновлення). Одночасно контейнер `protaxo_postgres` впав сам (exit 255) і не піднявся. Результат — застосунок з'єднався з порожньою нативною копією замість робочої, Flyway накотив усі pending-міграції на неї. Деталі й що з цим робити — [[База даних]] (розділ "Інцидент 2026-09-10"). Команда `Stop-Service` вимагає елевації — з неелевованого термінала/агента вона не спрацює (`Access is denied`), треба відкрити PowerShell "від імені адміністратора".

**Перед кожним запуском перевіряти, що відповідає саме Docker**:
```
docker ps --filter name=protaxo_postgres
docker exec protaxo_postgres psql -U postgres -d protaxo -c "select count(*) from clients;"
```
Якщо контейнер `Exited` — підняти (`docker start protaxo_postgres` або `docker compose up -d`) **до** запуску застосунку.

## Зміни в шаблонах/CSS вимагають перезапуску застосунку

`.\mvnw.cmd spring-boot:run` (і, відповідно, `run-app.ps1`) **не підхоплює** зміни в `src/main/resources/templates/**` чи `static/**` "на льоту" — немає spring-boot-devtools, тож класпас береться з `target/classes`, куди ресурси копіюються лише на етапі збірки, що виконується під час старту. Після редагування будь-якого `.html`-шаблону чи `style.css` **треба зупинити й заново запустити застосунок** (`Stop-Process -Name java -Force` для обох `java.exe`-процесів — Maven-обгортка й форкнутий JVM застосунку — потім знову `run-app.ps1`), інакше PDF/сторінки й далі рендеряться зі старої версії файлу навіть після збереження змін на диску. Виявлено 2026-09-17 під час перестилізації `pdf/invoice.html`.
