# Варіанти розгортання (сервер)

Обговорено 2026-09, рішення уточнено 2026-09-17. Мета: система має працювати автономно (без потреби тримати робочий ПК увімкненим), доступ — **приватний** (ніхто сторонній не повинен мати доступу).

## Рішення (2026-09-17): хмарний VPS, не власне залізо

Користувачка явно не хоче тримати сервер/БД фізично в себе вдома чи в офісі → варіанти "власного заліза" (Raspberry Pi / Mini PC / NAS / стара машина, таблиця нижче для довідки) відпадають. Обрано **хмарний VPS**.

### Уточнення (2026-09-19): конкретний провайдер — netcup, не Hetzner

Спочатку орієнтувались на Hetzner CX23 (2 vCPU/4GB/40GB, ~€4.5–5.5/міс) як найдешевший варіант. На момент вибору (вересень 2026) весь "cost-optimized" ряд Hetzner (CX/CAX) страждав від масового дефіциту — план розкуповувався за 20–30 хв після кожної появи в наявності в NBG1/FSN1/HEL1, замовити стабільно не вдавалось. Порівняли альтернативи (Kamatera ~$19/міс, netcup VPS Lite 1 G12s — €4.10/міс, але мінімальний термін договору 6 місяців з передоплатою одразу за весь період) — **фінально обрано Contabo, тариф "Cloud VPS 4"** (лінійку перейменували з 10/20/30 на 4/6/8/12 за кількістю ядер, це той самий початковий план): 4 vCPU / 8 GB RAM, NVMe, $4.95/міс, безкоштовна IPv4, оплата помісячно без довгострокового зобов'язання, ціна не підвищується при продовженні. Специфікації з запасом більші за мінімально потрібні (2 vCPU/4GB), але це найдешевший тариф лінійки — брати менший немає сенсу.

**Реальні параметри розгорнутого сервера (2026-09-19):** локація Hub Europe, IP `13.140.141.134` (перше замовлення випадково створилось у Sydney — виправлено зміною регіону в налаштуваннях, без потреби скасовувати замовлення), користувач `admin` (sudo, не `root`), Tailscale-адреса `100.96.72.33`, повне ім'я в tailnet `vmi3593666.tail3cfdbd.ts.net`.

**Важливо: "приватно" ≠ "фізично вдома".** Приватність доступу забезпечується не місцем розташування заліза, а мережевими налаштуваннями:
- Firewall провайдера — усі порти закриті, крім SSH (тільки з довіреного IP).
- **VPN (WireGuard/Tailscale)** на самому VPS — доступ до застосунку тільки через приватну мережу, порт застосунку/HTTPS не відкритий для всього інтернету.
- SSH тільки по ключу, без пароля.
- **HTTPS обов'язково** (Caddy як реверс-проксі) — трафік іде через реальний інтернет, не LAN, на відміну від поточного локального запуску.

### Практичний план

1. ✅ **`Dockerfile` для самого застосунку** (2026-09-19) — multi-stage build: `eclipse-temurin:21-jdk` збирає jar через `mvnw`, рантайм — `eclipse-temurin:21-jre` з layertools-екстракцією (кешування шарів, non-root user). `.dockerignore` виключає `target/`, `.git`, логи, бекапи з контексту білда.
2. ✅ **Продакшн `docker-compose.prod.yml` + `Caddyfile`** (2026-09-19):
   - Сервіси `app` + `postgres` + `caddy`, усі `restart: always`.
   - `app` і `postgres` **без `ports:` назовні** — доступні лише у внутрішній docker-мережі `internal`, наружу дивиться тільки `caddy`.
   - `caddy` слухає 80/443 **прив'язаний до `${TAILSCALE_IP}`**, а не `0.0.0.0` — порт фізично не існує на публічному інтерфейсі (firewall провайдера з п.3 — другий, незалежний рубіж).
   - HTTPS: `auto_https off` (звичайний ACME/Let's Encrypt однаково не спрацює без домену, відкритого в реальний інтернет) + справжній Let's Encrypt-сертифікат для `*.ts.net`-домену, випущений `tailscale cert` на хості й змонтований у `caddy` як `/certs` (без попереджень браузера, на відміну від початкового плану на `tls internal`).
   - Секрети — через `.env` (в `.gitignore`, не комітиться), шаблон значень у `.env.example`.
   - WebSocket Print Agent (`/ws/print-agent`) проксується автоматично, Caddy сам розпізнає `Upgrade`-заголовок.
3. ✅ **VPN на VPS (Tailscale) + firewall-правила** (2026-09-19) — `tailscale up --ssh` (дозволяє згодом закрити SSH-порт з інтернету повністю), `ufw` з `default deny incoming` + дозволом лише на `OpenSSH` і `tailscale0`, MagicDNS + HTTPS Certificates увімкнені в адмінці Tailscale.
4. ✅ **БД у тому ж Compose-стеку** (self-hosted Postgres, не managed DBaaS).
5. **Бекап-скрипт під Linux+cron** (аналог `scripts/backup-db.ps1`, той самий підхід — `docker exec ... pg_dump -Fc`), і копія **поза сам VPS** (3-2-1: якщо провайдер щось втратить — має лишитись копія деінде, напр. назад собі на комп'ютер чи в S3-сумісне сховище). Див. [[База даних#Бекапи]]. **Наступний крок.**
6. **Print Agent** — після переїзду вказати в конфізі IP/DNS нового сервера замість `localhost`, той самий `PRINT_AGENT_TOKEN` (env-змінна вже підтримана в `application.properties`). Див. [[Print Agent]].
7. Перед реальним використанням — змінити дефолтні паролі (БД, тестові акаунти `admin123`/`master123` з `AdminUserSeeder`) і реальний SMTP замість MailHog (наразі `MAIL_*` в `.env` порожні — застосунок працює, але листи-запрошення не надсилаються, доки не заповнити).

### Виправлені проблеми при першому розгортанні (2026-09-19)

- **`git clone <url>` без крапки в кінці** — репозиторій склонувався в підпапку `protaxo/protaxo` замість поточної директорії. Не критично, просто треба працювати з тієї вкладеної папки.
- **`./mvnw` не мав прапорця "виконуваний"** (`exit code 126`) — репозиторій вівся з Windows, git не зберігає unix-права доступу. Виправлено: `git update-index --chmod=+x mvnw` + явний `RUN chmod +x mvnw` у `Dockerfile` про всяк випадок.
- **`-Djarmode=layertools` не існує в Spring Boot 4.x** ("Unsupported jarmode 'layertools'") — перейменовано на `-Djarmode=tools` з прапорцями `--layers --launcher` (інший синтаксис команди, той самий результат).
- **Контейнер `app` падав у рестарт-луп** — `logback-spring.xml` пише AUDIT-лог у відносний шлях `logs/audit.log`, а непривілейований `app`-юзер у контейнері не мав ні директорії, ні прав її створити. Виправлено: `RUN mkdir -p /app/logs && chown -R app:app /app` перед `USER app` у `Dockerfile`, і `app_logs` named volume в `docker-compose.prod.yml` для персистентності логів між перезапусками контейнера.

## Розглянуті варіанти "власного заліза" (для довідки, не обрано)

| Варіант | Плюси | Мінуси |
|---|---|---|
| **Raspberry Pi** | Найдешевший вхід, низьке споживання | ARM-архітектура (треба перевіряти сумісність), SD-картка ненадійна для БД — **обов'язково USB SSD**, а не SD |
| **Mini PC** (Intel NUC, Beelink тощо) | Звичайна x86-архітектура (як на десктопі, без ARM-нюансів), потужніший за RPi, теж компактний і дешевий (~$150–300) | Трохи дорожче за RPi |
| **NAS** (Synology, QNAP) | Поєднує сховище + Docker (Synology Container Manager) в одному пристрої, вбудовані бекапи "з коробки" | Дорожче (від ~$200 без дисків) |
| **Стара/запасна машина** | 0 грн на нове обладнання, потужніша за RPi | Більше споживання електрики, гучніша/більша |

## Уточнення (2026-09-18): чому не хмарна керована БД (DBaaS)

Розглядали також повністю керовану хмарну базу даних (Amazon RDS, DigitalOcean Managed Database, Supabase, Neon тощо) замість self-hosted Postgres у тому ж Compose-стеку. **Відхилено** — суперечить вимозі "не видимий з інтернету": такі сервіси за замовчуванням дають базі **публічну адресу**, захищену лише паролем/TLS, тобто технічно доступну з будь-якої точки інтернету. Self-hosted Postgres на тому ж VPS, що й застосунок (пункт 4 вище), слухає лише `localhost`/приватну мережу — нуль зовнішньої поверхні атаки, узгоджено з рештою архітектури.

## Уточнення (2026-09-18): порядок онбордингу нового співробітника

Через **[[Реєстрація акаунтів (запрошення)]]** лист містить посилання `${app.base-url}/accept-invite?token=...`. Якщо `APP_BASE_URL` вказує на Tailscale-адресу сервера (а не публічний домен — так і задумано, щоб посилання теж працювало лише всередині приватної мережі), виникає залежність порядку дій:

1. **Спочатку** додати пристрій нового співробітника у tailnet (Tailscale admin console) — інакше посилання із запрошення для нього просто не резолвиться.
2. **Тільки після цього** створювати запрошення на `/users/new`.

Зворотний порядок (спочатку запрошення, потім Tailscale) означає, що перший клік по посиланню в листі не спрацює, доки людина не приєднається до мережі, — не критично (токен дійсний 24 год, можна перейти пізніше), але варто попереджати про правильний порядок, щоб не плутати користувача.

Пов'язано: [[Запуск проєкту]] (поточний локальний Docker-based запуск), [[Безпека і ролі]] (зараз лише HTTP, не HTTPS — обов'язково змінити перед виходом на VPS), [[База даних]] (бекапи), [[Реєстрація акаунтів (запрошення)]] (потік запрошень, `APP_BASE_URL`).
